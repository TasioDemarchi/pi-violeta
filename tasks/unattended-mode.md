# unattended-mode
Let the ODD orchestrator keep working after you walk away — until you turn it off — without stalling on a permission prompt nobody will answer.

> **This plan predates the cleanup of 2026-11-03.** `odd`, `scout` and `vault` were
> removed along with the agents `architect`, `planner`, `fixer`, `judge-a`, `judge-b`
> and `verifier`; `jarvis` is the only mode left. So T6 and the parts of S8 that name
> those files have nothing to edit, and the paths moved: `odd/tasks/` is now `tasks/`
> and `.odd/` is now `.violeta/`. The decisions below still hold; the file names do not.

## Decisions

D1. **Unattended denies and continues; it never pre-grants.** Every dialog the guard would open becomes a block with a reason, and the agent is told to adapt instead of retry. Pre-granting was rejected: a session nobody is watching that can run any destructive command is the one mistake nobody is awake to stop, and it would widen `OutsideGrants` from directory-scoped to global. The narrow door stays: a grant made interactively before activation keeps working.

D2. **There is no clock.** `/unattended on` runs until `/unattended off`; nothing expires, nothing is armed, nothing auto-disables, and no time is stored. The user's words are the specification: "quiero que funcione hasta que yo lo vuelva a desactivar". Two consequences decide the rest of this document. First, a deadline that re-opens dialogs at 3 a.m. for nobody is the exact hang the feature exists to remove, so expiring is not a safety feature. Second, with no clock the destructive guard is the **only** automatic stop that remains: its coverage is the entire safety story, which is why D5 and D6 pull two guard gaps into scope instead of filing them for later. Rejected along with the clock: any default duration or TTL, an inactivity timeout, a "safety" auto-off, and the restart breadcrumb — the breadcrumb existed only to report a deadline that had been lost, and the hub is per process and never persisted, so there is nothing to leak and nothing to warn about.

D3. **Unattended never commits, in every process.** §11 of `modes/odd.md` already makes commits, pushes and PRs the user's call; `git commit` is the one form the destructive matcher does not cover, so unattended blocks it. The block holds where the command actually runs: the guard loads in subagents too (`src/agents/runner.ts:296`), and the flag reaches each child (D8), so a builder that decides to commit is blocked in its own process and not only in the orchestrator's. The work stays in the working tree and in the feature document for review. Push already needs a confirmation, which unattended blocks; PRs stay prompt-level.

D4. **Read is granted outside the project; write is not — and the boundary is the tool, not the command.** While unattended, `read`, `grep`, `find` and `ls` on any path work with no dialog and record no grant; `write` and `edit` outside stay blocked; `bash` with an outside path stays blocked and its reason names `read`, `grep`, `find`, `ls`. The reason `bash` is not widened with the read tools: a shell command does not declare whether it reads or writes — `cat ../other/x` and `echo x > ../other/x` differ by one redirect — so allowing shell outside paths means deciding per command what a shell does, and the cost of deciding wrong is a write outside the project, the single thing the requirement forbids. Rejected: (a) an allowlist of read-only heads (`cat`, `head`, `grep`, `find`) — that is the per-command argument model the previous revision already rejected as out of scope, and `cat ../x | tee ../y` walks straight through it; (b) giving shell the same pass as the read tools and trusting the destructive matcher — the matcher has no notion of redirects, so `echo x > ../y` would go through. The block is not a dead end: the four read tools do the actual work, and the reason says so.

D5. **A write outside the project through a shell is closed where it is decidable.** Redirect targets (`>`, `>>`, `&>`, `2>`, spaced or glued) and `dd`'s `of=` value become path targets of the existing `bashPathTargets`, so an outside one is a block while unattended and an ordinary grant dialog interactively — one rule in one function instead of a second mechanism. Rejected: adding `mv` and `truncate` to the destructive matcher. `mv` inside a project is a normal refactor that would prompt on every rename, `dd of=/dev/*` and `mkfs` are already matched today, and the harm the rest of them can do outside the project is exactly what the path rule now catches.

D6. **What the guard deliberately will not see is written down, not ignored.** Not covered, by decision: variable expansion and `$(...)`, `python -c` / `node -e` that opens a file, payloads piped through `base64`, shell functions and sourced scripts, `mv`/`truncate` inside the project, and any command whose destructiveness is only knowable by running it. This is a command-line recognizer, not a sandbox: a determined agent can evade it. The feature protects against the plausible mistake the user named ("no pueda ejecutar comando que puedan romper cosas"), and pretending otherwise would cost a sandbox nobody asked for.

D7. **A session toggle on the shared hub for this process plus one env var for the child; not a mode, not a CLI flag.** Guard, agents and mode load as separate module instances and the hub is the established channel (`src/shared-hub.ts`). The hub is per process (`Symbol.for` on `globalThis`), which is exactly why it cannot be the whole answer: the runner sets `VIOLETA_UNATTENDED=1` on each child it spawns, and `unattendedActive(session, childFlag)` in `src/unattended/state.ts` ORs the two — one predicate, read by the guard (the only extension that must enforce anything) in both processes. Pi has no unattended flag, so an argv flag would need launcher parsing plus a read in every entry point; the env var is written at the one spawn point that already exists. A mode is philosophy (prompt text), not a capability switch, and modes persist in `violeta.json` — this must not survive a restart.

D8. **The flag crosses the process boundary at spawn, as an env var plus a prompt clause, passed in by the caller.** `SubagentRunner.launch` already builds the child env and already writes the child's `--append-system-prompt` file, so it asks `RunnerOptions.unattendedClause()` once per launch: text means `VIOLETA_UNATTENDED=1` and the clause appended to the prompt; `undefined` means neither. Rejected: propagating the hub to children (there is no channel — they are separate `pi` processes, and `globalThis` never crosses), reading the hub in the guard as the only source (undefined in a child: the gate's finding), an argv flag (D7), and the runner importing `getShared()` itself (its header promises a neutral engine with no violeta philosophy; a caller-supplied callback keeps it neutral and is re-read per launch, so the runner cached in `getRunner()` can never carry a stale flag). Nothing is retroactive: a child spawned before activation keeps its old rules and ends at its ceiling.

D9. **The child-facing "a block is final, adapt, never retry" clause comes from the runner, not from `violeta-mode.ts` and not only from the shipped definitions.** Children never load `violeta-mode.ts` (it returns early on `VIOLETA_AGENTS_CHILD=1`), so the orchestrator's block cannot reach them; and definitions are user-editable markdown, so a user-created agent would miss it. Appending it to the child's system prompt covers every definition, shipped or not. Rejected: putting the rule in every definition as permanent policy (it would then read as house style always, and user definitions still miss it — the ceiling rule stays there because it is house style).

D10. **Nothing is remembered between processes.** The toggle lives on the hub, `session_start` clears it, and no file is written, so a new process starts interactive. `/unattended` never restores and never warns; the user turns it back on. Rejected: persisting the flag in `violeta.json` (D7) and the breadcrumb of the previous revision (D2).

D11. **The `bashPathTargets` slash-in-pattern false positive is not fixed and is not a blocker.** `sed -n '/p/,+Np'` reads as an outside path. Fixing it needs a real per-command argument model; narrowing quoted tokens would stop guarding `cat "/etc/passwd"`, which is worse than the false positive. Under D1 the false positive is a block with a reason that names the read tools and `/unattended off`, not a hang.

## Specs
S1. `/unattended` is a registered command and the only control. With no argument it reports the state: when off the text contains the literal `/unattended on`; when on it contains `activo desde`, `git commit`, `solo lectura` and `/unattended off`. `/unattended on` turns it on and notifies `t.unattended.activated`; when already on it is a no-op that reports the same status as the no-argument form. `/unattended off` turns it off and notifies a text containing `desactivado`. Any other argument prints exactly `uso: /unattended [on | off]` and changes nothing. The activation notice contains `/unattended off` and the four literals `no se van a responder` (dialogs will not be answered), `No se commitea nada`, `se pierde al reiniciar` (the flag does not survive a restart, D10) and `ya están en marcha` (subagents already running do not inherit it). State is `getShared().unattended` (`UnattendedSession`, carrying only `startedAt: number`), never written to `violeta.json`, and `session_start` clears it. Activating does not start a turn (`sendMessage` is never called by the command). No duration, deadline or expiry exists anywhere in the state.
    Accept: each form produces the stated hub state and text (the notice contains all five substrings), the invalid form leaves the previous state untouched and prints the usage line exactly, `on` twice leaves `startedAt` unchanged, a fresh process is off, and `session_start` leaves the hub without an `unattended` key. The named `/unattended off` is a real registered handler that clears the state.
    Check: `node --test --test-name-pattern='unattended command|unattended session start' tests/unattended.test.ts`

S2. While `unattendedActive(getShared().unattended, process.env.VIOLETA_UNATTENDED)` is true — a hub session (orchestrator) or `VIOLETA_UNATTENDED=1` (a child, S10) — `extensions/violeta-guard.ts` never calls `ctx.ui.select` and never publishes `notifyNeedsAnswer: true` on the hub, even when `ctx.hasUI` is true. A destructive match returns `{ block: true }` whose reason starts `Modo desatendido:`, contains the matched reason, states that the command did not run and that nobody can approve it, and ends naming `/unattended off`. Catastrophic targets keep today's `t.guard.catastrophic` denial text unchanged. A directory already granted in this session is still allowed, with no dialog and no block. `/unattended off` restores the dialog: the next destructive match calls `ui.select` again, which proves the command named in the reason resolves.
    Accept: the tests drive the guard's exported `tool_call` handler with a mock `ctx` and assert no dialog, no `notifyNeedsAnswer`, the reason substrings, that a prior grant still passes, and that the dialog returns after `off` invoked through the real `/unattended` command handler rather than a hand-cleared hub.
    Check: `node --test --test-name-pattern='unattended guard' tests/unattended-guard.test.ts`

S3. In unattended mode a shell call whose executable is `git commit` is blocked in every process that carries the flag (the hub session in the orchestrator, `VIOLETA_UNATTENDED=1` in a child — S10 asserts the child) before the destructive check, with a reason containing `git commit`, the exact command, and `/unattended off`. Detection shares the existing git action parsing, so `git -C dir commit -m x`, `sh -c 'git commit -m x'` and `eval "git commit -m x"` are caught, while `git log --grep commit` and `git commit` with unattended off are not blocked. The matcher is a pure export `gitCommitIn(command)` from `src/guard/command-guard.ts` (it reuses `tokenize`, `headCursor` and the `sh -c`/`eval` recursion); every existing destructive decision is unchanged.
    Accept: the matcher unit cases fail before the change and pass after; the orchestrator's block is asserted in the guard test; the existing `guard-command` destructive tests stay green.
    Check: `node --test --test-name-pattern='unattended commit|destructive' tests/unattended-guard.test.ts tests/guard-command.test.ts`

S4. While unattended, outside-project **reads** work and outside-project **writes** do not. For `read`, `grep`, `find` and `ls` with a `path` that resolves outside `ctx.cwd` (and outside `PI_CODING_AGENT_DIR`), the guard returns no block, calls no `ui.select`, publishes no `notifyNeedsAnswer`, and records no grant — `/grants` lists exactly what it listed before. For `write` and `edit` with such a path the guard returns a block whose reason names the resolved directory, contains `solo lectura` and `fuera del proyecto`, and names `/unattended off`; no dialog is opened. Paths inside `ctx.cwd` or inside `PI_CODING_AGENT_DIR` behave exactly as today in both modes, and with the flag off all six tools ask for a grant exactly as today.
    Accept: the guard test drives all six tools against the same outside path while unattended — four return `undefined` with zero `selects`, two return the block with its substrings — then repeats `read` after `/unattended off` and gets the grant dialog; `getShared()` never carries `notifyNeedsAnswer` during the unattended calls and the grants list is unchanged.
    Check: `node --test --test-name-pattern='unattended outside' tests/unattended-guard.test.ts`

S5. While unattended, a shell call (`bash`, `bash_background`, `monitor`) whose `bashPathTargets(command, ctx.cwd, home)` is non-empty is blocked with `Modo desatendido:` as its prefix, a reason naming the first resolved target, naming `read`, `grep`, `find` and `ls` as the way to read it, and naming `/unattended off`. That includes a bare `cd` or `pushd`, which contributes `$HOME` (S6) and is blocked whether or not anything follows it. `cat ../other/x` is blocked while `read` on the same path is allowed (S4). A shell call with no outside target is unaffected, and with the flag off the outside-path branch asks for a grant exactly as today. The shell branch's blocks run in this fixed order: `gitCommitIn` (S3), then `guardDecision` (its `deny` for a catastrophic target, its `block` when nobody can ask), then the outside-path block — so `rm -rf /`, whose `bashPathTargets` is `["/"]`, keeps the catastrophic denial instead of being answered with the read-tools text.
    Accept: the guard test blocks `cat ../other/x`, `ls /tmp/otro`, `git -C /otro status` and `cd && echo x > .bashrc` (reason naming the home directory) while unattended with the reason substrings, allows `cat README.md`, `npm test` and `cd /repo && echo x > out.txt`, asserts the read tools still pass on the same paths in the same session, and asserts `rm -rf /` while unattended carries `Objetivo catastrófico denegado sin preguntar:` and not the outside reason.
    Check: `node --test --test-name-pattern='unattended outside|unattended shell' tests/unattended-guard.test.ts`

S6. An outside write through a redirect is an outside path, and so is leaving the project by directory. `bashPathTargets(command, dir, home)` in `src/guard/paths.ts` takes ONE directory as both cwd and root; it also returns, resolved with the same `resolvePath`, the target of every write redirect (`>`, `>>`, `&>`, `2>`, with or without a space after the operator, and `>|`, split off the token they are glued to — `2>&1`/`>&2` are descriptor duplications, not targets), the value of `of=`, and `$HOME` for every segment whose head is `cd` or `pushd` with no argument or with `-` (`cd -` reads OLDPWD, so `$HOME` is the conservative stand-in). Redirect targets are resolved without the `isPathLike` gate, since `out.txt` has no slash; targets that resolve inside the root are dropped by `isInside`, exactly as today; `/dev/null`, `/dev/stdout` and `/dev/stderr` are ignored everywhere. The scan recurses into `sh -c '...'`, `bash -c "..."` and `eval "..."` payloads the way `gitCommitIn` does in S3, reusing that extraction inside `paths.ts` rather than importing `command-guard.ts`, so the quoted payload is not a blind spot here either. Concretely: `bashPathTargets("echo x >/etc/passwd", "/repo", HOME)` is `["/etc/passwd"]`; the same command as `sh -c 'echo x >/etc/passwd'` is `["/etc/passwd"]`; `bashPathTargets("echo x >> ../outside/x", "/repo/sub", HOME)` is `["/repo/outside/x"]` (the root is `/repo/sub`, so that is outside it); `bashPathTargets("dd if=zero of=../outside/x", "/repo/sub", HOME)` is `["/repo/outside/x"]`; `bashPathTargets("cat ../other/x", "/repo/sub", HOME)` stays `["/repo/other/x"]`; `bashPathTargets("cd && echo x > .bashrc", "/repo", HOME)` is `["/home/tasio"]`; `bashPathTargets("pushd && echo x > .bashrc", "/repo", HOME)` is `["/home/tasio"]`; `bashPathTargets("cd - && echo x > y", "/repo", HOME)` is `["/home/tasio"]`; `bashPathTargets("cd /repo && echo x > out.txt", "/repo", HOME)` is `[]`; `bashPathTargets("npm test > /dev/null 2>&1", "/repo", HOME)` is `[]`; `bashPathTargets("echo x > out.txt", "/repo", HOME)` is `[]`. When the root is `$HOME` itself that `cd` value is dropped like any other inside-root one. Nothing in `recognizeDestructiveCommands` or `guardDecision` changes, and every existing `guard-paths`, `guard-grants` and `guard-command` test stays green.
    Accept: the new `redirect` and `leaves project` cases in `tests/guard-paths.test.ts` fail before the change and pass after; the existing path, grant and destructive suites are unchanged.
    Check: `node --test --test-name-pattern='redirect|leaves project' tests/guard-paths.test.ts`

S7. While `getShared().unattended` is set, the append built by `extensions/violeta-mode.ts` on `before_agent_start` includes a block `t.unattended.prompt` that (a) names autonomy level 2, (b) says no confirmation will arrive and a guard block is final — adapt, never retry the same command, (c) forbids `git commit`, `git push` and PRs, (d) says reading outside the project is allowed through `read`, `grep`, `find` and `ls` while writing outside it and shell commands that leave it are blocked, and (e) forbids waiting for the user: record the open question in the document and continue. When off the block is absent. It is appended after the mode body and never replaces `event.systemPrompt`. This is the orchestrator's copy only: children never load `violeta-mode.ts`, so the child-facing copy comes from the runner (S10).
    Accept: the same test toggles the hub and asserts the block appears and disappears; when appended to an existing `appendSystemPrompt` it follows it; the block contains `nivel de autonomía 2`, `git commit` and `solo lectura`.
    Check: `node --test --test-name-pattern='unattended prompt' tests/unattended-prompt.test.ts`

S10. Unattended is enforced where the command runs, not only in the orchestrator's process. At every child launch `SubagentRunner.launch` calls `options.unattendedClause()`: when it returns text the child env carries `VIOLETA_UNATTENDED: "1"` and that text is appended to the temporary `--append-system-prompt` file after the definition prompt; when it returns `undefined` the variable is absent and the prompt is the definition unchanged. `extensions/violeta-agents.ts` supplies `() => getShared().unattended ? t.unattended.childPrompt : undefined`, evaluated per launch, so a cached runner never carries a stale flag. `unattendedActive(session, childFlag)` in `src/unattended/state.ts` is the single predicate the guard uses (S2), so in a child with an empty hub the env var is what makes the block fire. Nothing is retroactive: a child spawned before activation does not gain the flag (D8).
    Accept: the guard driven with `VIOLETA_AGENTS_CHILD=1` and `VIOLETA_UNATTENDED=1` over an empty hub blocks `git commit -m x` with `git commit` and `/unattended off` in the reason and never calls `ui.select`, while the identical call with neither variable is not blocked — this is the assertion that was missing when the gate found the hole; and a fake-spawned runner records `VIOLETA_UNATTENDED === "1"` with the clause present in the written prompt file when the callback returns text, and neither when it returns `undefined`.
